**已落地**（`sidebar.rs view_nav` / `paint_nav_tab` / `nav_tab_center`）

改前（130px）              改后（26px）
┌────────────┐            ┌────────────┐
│ 📁 文件      │ ← 选中     │ ▣▣▣▣▣      │ ← 26px，下缘横条表选中

│ 🔗 链接      │            │            │

| 决策 | 选择 | 理由 |
|---|---|---|
| 排列 | 横排五枚 26×26 tab | 5×26+4×2 = 138px ≤ `SIDEBAR_MIN_W` 180，窄栏也放得下 |
| 选中态 | 圆角底 + **下缘 2px 横条** | 横排时左侧竖条会指向相邻 tab（"所属行"已读不出来）；横条与 `ui::tabs` 页签下划线同构 |
| 标签 | 只给 tooltip，不给常驻文字 | 常驻文字在 180px 下限会换行（`top_actions` 已有前例） |
| 命中区 | 整枚 26×26 | 不是仅图标 |
| `NAV_ROW_H` | 标废弃但**保留** | 旧 commit 的测试按名字引用它，删常量破坏 `git bisect` |
| `icon_label_row` | 标 `#[allow(dead_code)]` 保留 | 同上；它记录了「整行选中态」的画法 |

**测试**：`nav_tab_center_x_follows_tab_order`（顺序 helper 改 x 轴）、
新增 `five_nav_tabs_fit_the_narrowest_sidebar`（138 ≤ 180，改版前提）、
`clicking_nav_tab_switches_view`（点击路径 + 落点在段内的 sanity 断言）。

### 2.1 一条测试纪律：断言上界不许复用绘制 token

`three_bands_fill_the_panel_top_down` 断言 nav 段高度 ≤ 40px。这个 40
**刻意硬编码，不读 `NAV_TAB_H`**。

原因：段高由 `set_min_height(top + NAV_TAB_H)` 报告，与绘制**同源**。
若上界也读 token，把 token 调大（哪怕是误改）会让绘制与断言一起变大 →
断言自我满足。红绿验证实测：

| 断言写法 | 模拟回退（`NAV_TAB_H` 改 130） | 结论 |
|---|---|---|
| 上界 = `NAV_TAB_H + SEP + 1` | **绿**（133px ≤ 134px） | ❌ 失效 |
| 上界 = 硬编码 `40.0` | **红**（133px > 40px） | ✅ 有效 |

**通则**：断言「不超过某量」时，上界必须独立于被断言的实现。

## 3. S1-2 状态栏：单一顺排 → 三段分区

**已落地**（`layout.rs status_bar`）

```
改前                          改后
文件名 行21:1 · 248字 ·        文件名 行21:1     248字        浅色 · Mock · MCP: 8731
浅色 · Mock · MCP: 8731       └─ 左 ──────┘  └ 中 ┘  └──────── 右 ────────┘
└──── 全部挤在左端，右端空 ────┘
```

| 段 | 内容 | 理由 |
|---|---|---|
| 左 | 文件名 · 行:列 | 最高频，与文档强绑定 |
| 中 | 字数 | 写作进度感，与左右都无关联 |
| 右 | 主题 · AI provider · MCP | 全是**全局服务状态**，彼此相关，应聚在右端一眼扫完 |

**核心收益不是「好看」，是告警位置**：`MCP: 启动失败` 是状态栏里唯一
必须被盯到的动态项，改版前它偏在最右、要横跨整屏才看到；改版后恒在
右下角，与视线停留点一致。

| 决策 | 选择 | 理由 |
|---|---|---|
| 右段布局 | `Layout::right_to_left` | 零参数、自动贴边、窗口拉伸无需同步改数字 |
| 段内顺序 | push 顺序即从右到左 | MCP 第一个 push → 画在最右 |
| 窄窗口 | 中段整段不画（`STATUSBAR_MIN_W=240`） | 字数是三者里唯一丢了不影响操作的；**绝不让 MCP 告警被挤出可视区** |
| `separator()` | 删除 | 三段本身已表达分组，`·` 分隔符反而暗示「同组」 |

**不用 `layout_to_min_x` 的理由**：它要求调用方自己算百分比 x，三段各写
一个 magic number；「左中顺排 + 右段 `right_to_left`」是零参数写法。

## 4. S2-3 侧栏与内容区拉开明度差（已落地）

**已落地**（`theme.rs shell_tokens`，两套主题各改一个 `sidebar` 值）

| 主题 | 改前 | 改后 | 与 content 的对比度 | 通道差 |
|---|---|---|---|---|
| 浅色 | `#F2F3F5` | **`#EDEFF2`** | 1.110:1 → **1.135:1** | 13 → **18** |
| 暗色 | `#202124` | **`#1B1C1F`** | 1.122:1 → **1.196:1** | 9 → **14** |

两条不同的上限约束：

- **暗色可以更深**：侧栏越沉，内容区越「浮起来」。但再深就与窗口底色
  撞上，侧栏会读成「挖了个洞」而不是「背景层」。
- **浅色到此为止**：`#EDEFF2` 是「仍浅于 `border`（`#E5E6E8`）一档」的最深值。
  再深一档到 `#E4E6EA` 就与 border 撞色，**侧栏里的分隔线会消失** ——
  浅色下分隔线比底色差更重要，这条由 `light_sidebar_stays_lighter_than_border` 钉住。

**hover 保持 `#F2F3F5` 不动**：它比新 sidebar 深，于是 hover 在侧栏里表现为
「一块更深的斑」而非「提亮」。侧栏整体退到背景层后，hover 若也提亮会与
选中态 `selected_bg`（`#E1EFFF`）争夺注意力。

**影响面已核**：`panel_fill = sidebar`（`theme.rs:592`），而 9 套出厂预设是
`MarkdownStyle`（**只管正文，不含 sidebar 色**），故改一处两套主题全生效，
预设不受影响。吃 `panel_fill` 的位置共 9 处（`layout.rs` 4 + `titlebar.rs` 2 +
`zen_nav.rs` / `selection_ai.rs` / `icons.rs`）。

### 4.1 三条断言（把「可辨」钉成测试）

| 断言 | 锁的是 |
|---|---|
| `sidebar_and_content_are_distinguishable_in_both_themes` | 对比度 ≥ **1.12:1**（明暗各测） |
| `light_sidebar_stays_lighter_than_border` | 浅色 sidebar 亮度 > border 亮度 |
| `sidebar_content_delta_stays_in_the_readable_band` | 通道差落在 dark [12,18] / light [16,22] |

阈值 **1.12:1** 是从改版前的实测值反推的（1.110 / 1.122 都被判为「看不出差」）。
参照物说明：WCAG 1.4.11 的 3:1 针对**UI 组件边界**（按钮/输入框的可点击轮廓），
**不适用**于「相邻面板的背景分区」；按 3:1 做会把侧栏压成深灰、观感受损。
所以这三条只锁「可辨」，不锁「达到无障碍标准」—— 两者不是一回事。

**第三条（上界）防的是反向坑**：把 sidebar 一路加深到接近窗口底色，
三栏会从「分不开」变成「侧栏太重」。

红绿验证：把浅色值改回 `#F2F3F5` → 前两条当场变红
（`1.110:1 < 1.12`、`通道差 13 ∉ [16,22]`），还原后绿。

## 5. S2-2 格式工具条：17 按钮平铺 → 8 直出 + 溢出菜单（已落地）

**已落地**（`compose.rs` 的分组划分 + `format_bar.rs` 的绘制）

治症状 D：十七个按钮**等权重**平铺，四组的视觉分段只靠一根 1px 竖线，
`B I S` 用字母而其余用自绘线段 —— 扫读成本高，且低频动作（标题/块）
与高频动作（行内）占据同等显眼的位置。

| | 改前 | 改后 |
|---|---|---|
| 常驻按钮 | 17（+ emoji = 18 槽位） | **8**（行内 5 + 列表 3） |
| 溢出 | 无 | 「更多」菜单：**9** 项（标题 4 + 块 5） |
| 可见槽位 | 18 | **10** |

**实测收益（2026-10-08 补，headless 量 `min_rect`）**：

| 可用宽 | 改前 | 改后 | 差 |
|---|---|---|---|
| 宽档（≥568） | 568 × 30（1 行） | **331 × 30（1 行）** | **宽度 −237px** |
| 420 | 420 × 63（2 行） | **331 × 30（1 行）** | 高度 −33px |
| 280 | 272 × **96（3 行）** | 250 × **63（2 行）** | 高度 −33px |
| 240（= 最小窗编辑区宽） | 228 × **96** | 240 × **63（2 行）** | 高度 −33px |

**主要收益是宽度不是高度**：自然宽 568 → 331 省 237px；省下的宽度在**窄栏**
里转化为行数（3 行 → 2 行，−33px），在宽档里则表现为「同样宽度下少占位」。
此前只写「省 30px 常驻」，既没说清是宽度收益、也漏了窄栏这一档。

依据 ui-polish §1.2「工具栏只留高频动作，其余收进设置，**可发现性由菜单栏
负责**」—— `FORMAT_MENU` 早已收了全部 17 个格式动作，菜单栏才是全量入口，
工具条只是快捷面，**可发现性不丢**。

### 5.1 设计被守门测试当场打回：列表组必须直出

首版只留**行内组**直出（5 项），把列表组也塞进菜单。第一次跑全量测试就红：

```
ui::layout::tests::task_button_cycling_on_cjk_never_panics
  探针拿到 Task 按钮:[0.0 0.0]
```

原因是漏算了一条**多步交互**的代价：`Task` 是十七个动作里唯一的三态循环
（`- [ ] `→`- [x] `→`- `），进菜单后每次点击都关菜单，**一次状态切换要
「开菜单 + 点」×3 = 6 次点击**，比改版前的 3 次更差。

按「点击总次数」算，列表组才是高频 → 列表组改回直出。
**这条是护栏测试的正面价值：不是事后补的，是当场拦下的设计缺陷。**

### 5.2 探针在菜单内也生效（否则十二项失去覆盖）

`ui_with_probe` 的 `probe` 回调在**菜单闭包内部**同样触发。这是刻意的：
无头测试据此在菜单打开后定位条目矩形。若探针只对直出按钮生效，
菜单里的动作**没有任何测试能点得到** —— 九个低频动作的点击路径会静默失去
覆盖，且「探针对菜单无效」这件事本身不报任何错。

`clicking_image_requests_the_dialog_not_a_format` 据此重做为三段：
定位「更多」文本 → 点开 → **两次空帧**（egui 0.36 的 MenuButton 从 popup
记忆开态到闭包真正绘制隔一帧，与 `menubar.rs` 同款时序，见
decisions-pending #128）→ 探针取 Image 矩形 → 点击。

### 5.3 两条守门测试（职责不重叠）

| 断言 | 锁的是 |
|---|---|
| `direct_and_overflow_cover_every_group_exactly_once` | `DIRECT ∪ OVERFLOW` **恰好**覆盖四组，不多不少无重复 —— 防将来加第五组时被静默遗忘（不报编译错、菜单栏照常有、只有常驻按钮不见了） |
| `direct_row_is_inline_plus_list_only` | 具体划分 + **收益量化**（直出 8 / 溢出 9 / 合计 17 一项不少） |

另在 `ui_with_probe` 里有同款 `debug_assert!`（生产路径，release 下不付
检查成本）。

**一个测试设计教训**：这两条断言最初写成 `assert_eq!(DIRECT, [Inline])`
—— 数组长度一变，`[T; 2] == [T; 1]` 是**编译错误**而非断言失败。守门测试
若以「编不过」的方式拦回归，就不是守门测试，而是一根会误伤正确改动的
拦路桩（首版红绿验证时才发现）。改为 `.as_slice()` 比较后，
长度变化退化成正常断言失败。

### 5.5 左缘 rail：顶部 11 枚迁入竖向图标带（2026-10-08，用户指定）

治症状 B 的**下半场**。§2 把视图导航从竖排五行压到单行后，左栏顶部仍留
着**两条**横向占用（顶段文件动作 31px + nav 段 26px，窄栏下前者换行成
62px）。rail 把这两者一并收进左端一条**竖**带：

```
改前（180px 窄栏 88px chrome）      改后（0px）
┌──────────────┐                  ┌────┬────────┐
│ ▣▣▣▣▣      │ ← nav 26px        │ ▣  │ 文件树  │
│ ⊞⊟⤓⤒⋯⋯    │ ← top_actions     │ ▚  │ （+88） │  ← 顶部零 chrome
│ ├────────────┤                  │ ⊞  │        │
│ 文件树        │                  │ ⊟  │        │
└──────────────┘                  └────┴────────┘
                                   rail   body
```

| 决策 | 选择 | 理由 |
|---|---|---|
| rail 位置 | 画在**左栏内部**，占左端 48px | 若开第四个 `Panel::left`，左栏总占宽 240 → 288，**编辑区净损 48px** —— 省下的纵向 chrome 会以横向形式赔回去 |
| 收录范围 | 上组五视图 + 下组六文件动作，共 11 枚 | 用户指定「文件动作也进 rail」；自此左栏顶部**无任何横向条带** |
| 取代 relation | **完全取代** §2 的单行 `view_nav` | 并存会退化成「又一处占用」，且与减 chrome 的初衷相悖 |
| 选中态 | 从「下缘横条」换回「**左缘竖条**」 | 竖排态下竖条的「所属行」读得出来；横排时它会指向相邻 tab —— 这正是当年改横条的原因，排布翻了，结论也翻 |
| 禅定模式 | 不显示 | `draw_zen` 走**另一套 panel 组合**（压根不加左栏），天然满足；且禅定已有 #57 左缘悬停导航，两者并存会抢 hover 区 |
| 旧函数 | `view_nav` / `top_actions*` / `paint_nav_tab` 保留打 `#[allow(dead_code)]` | 同 `NAV_ROW_H` 的 `git bisect` 纪律：删了旧 commit 无法复现 |

#### 5.5.1 一条踩出来的 egui 事实：`allocate_rect` 不吃游标

rail 用逐枚 `allocate_rect` 摆**绝对**矩形，这些方法**不推进 `Ui` 的游标**
（不像流式布局的 `horizontal`）。故不能指望 body 的 `ScrollArea` 「顺势」
排在 rail 之后 —— 实测它会从第 11 枚按钮下方起排（body.top = 351px）。
正解是把 body 显式下到一个 `max_rect` 已截好的子 Ui：

```rust
let mut body = panel.new_child(UiBuilder::new().max_rect(body_rect));
ScrollArea::vertical().show(&mut body, |ui| …);
```

与 ① 标题栏那条（子 Ui 必须限 `max_rect`，否则读到 900×600 根矩形）是同一
类坑的两个方向。

#### 5.5.2 两条测试必须从退役函数迁到 rail（否则是假绿）

改完第一遍全量 893 绿，但 `clicking_every_top_action_sends_its_command`、
`hovering_top_action_shows_shortcut_tooltip` 这两条测的仍是 **`#[allow(dead_code)]`
保下来的 `top_actions_with_probe`** —— 函数在、测试绿，可生产路径已不再调它。
**「测退役函数」比「没测试」更危险**：它给出虚假的安全感。两条已改写为
`clicking_every_rail_action_sends_its_command` / `hovering_rail_action_shows_
shortcut_tooltip`，直驱 `draw_rail`。

#### 5.5.3 红绿验证抓到一个失效断言

`rail_and_body_split_the_sidebar_left_to_right` 初版把 rail 宽度上界写成
`≈ RAIL_W`。按 §2.1 的纪律这是**自我满足**的 —— 实测把 `RAIL_W` 改成 96
模拟回退，断言照样绿（绘制与断言一起变宽）。改为硬编码 `56.0` 后当场红。

| 验证 | 回退方式 | 结果 |
|---|---|---|
| body 与 rail 并排 | body 矩形起点从 `max_rect().top()` 改成 `strip.bottom()` | ✅ 红（差 600px） |
| rail 宽度上限 | `RAIL_W` 48 → 96 | 初版**绿**（失效）→ 改硬编码 56 后 ✅ 红 |

> **这条印证了 §2.1 不是一次性的提醒**：同一个人在同一份文档周期内，
> 换一个场景照样会写出自我满足的断言。结论应变成肌肉记忆 —— 凡是
> 「不超过某量」的上界，先问一句「它是不是也从同一个 token 算出来的」。

### 6.1 S2-1 主动暂停（2026-10-08 决策，不是放弃）

标签条并入标题栏 —— 收益 28px（约窗口高 4.7%），**评估后决定暂不做**。

| # | 理由 |
|---|---|
| 1 | **风险/收益比差**：28px 要换的是**无边框窗口的拖动区** —— 全项目最不能出错的地方（拖不动窗口 = 产品不可用） |
| 2 | **刚在低复杂度改动上栽过**：状态栏三段（三个平级调用）就出了 1386 测试全绿都漏掉的回归（见 §8 与 PR #137），S2-1 复杂度高一个量级 |
| 3 | **拖动行为会真退化**：标签条是 `ScrollArea`，会**吃满标题栏给它的那段宽度**；标签之间的空隙归 ScrollArea 而非背景 → **在标签区空白处拖不动窗口**。现在标签条在编辑区上方，拖不到窗口，改完就是净损失 |
| 4 | **Zen 行为要额外守住**：Zen 下 CentralPanel 不画标签条；标签条上移后会在 Zen 里凭空出现 —— 这是行为变更，不是纯布局调整 |
| 5 | **技术上可行但非平凡**：标题栏是绝对矩形绘制（背景 rect + `button_rects` 左右两段），标签条是流式布局（`ScrollArea` + `horizontal`）。`UiBuilder { max_rect }` + `scope_builder` 能在指定矩形内建子 Ui，但标题文本宽度是变的（`window_title()`），防重叠得先量文本宽 |

**更安全的替代方案**（若确要那 28px）：把**标签条与格式条并到同一行**。
两者都已在 CentralPanel 的流式布局里 —— 不碰窗口 chrome、不碰拖动区、
不改 Zen 行为。

> **⚠️ 2026-10-08 实测后否决**：此替代方案**不成立**。最小窗口 900px 下
> 编辑区 = 900 − 240（侧栏）− 420（预览）= **240px**，而格式条**单行就要
> 331px**（实测），在 240px 下它自己已是 2 行 63px。标签条塞不进同一行，
> **省不到任何空间**。
>
> 精确条件：并到一行只在**编辑区 ≥ ~480px**（格式条 331 + 2~3 枚标签 ~120
> + 间隙）时才成立 —— 即窗口 ≥ ~1140px，或**关掉右预览**（编辑区 660px）。
> 故它不是「更安全的替代」，而是「另一种窄栏失效的形态」。

**结论升级（2026-10-08 实测后）**：S2-1 **在当前最小窗口尺寸下无任何可行
形态**。标题栏路线有拖动退化（理由 3），并排路线连空间都不够（见上方否决）。
真要那 28px，只有三条路：

| 方案 | 代价 |
|---|---|
| 提 `min_inner_size` 的高度（600→640） | 最小窗口变大，小屏用户吃亏 |
| 降 `PREVIEW_DEFAULT_W`（420→340）给编辑区让宽 | 预览默认变窄，**不省高度**（只让并排方案可行） |
| 接受拖动退化 | 不推荐 |

**重启条件**：窗口默认高度显著变大、或编辑区常态宽度 ≥480px（并排方案成立）、
或出现「标签条必须贴文档标题」的新需求。

### 6.2 S3-1 规格已落定，待 #68 落地后实现

症状 E「minimap 像第三栏」。**规格先定，实现等 #68**。

#### 现状（代码事实，非目测）

| 项 | 值 | 出处 |
|---|---|---|
| 条带宽 | `MINIMAP_W = 108.0`（其中最右 10px 是滚动条避让区，真实条宽 ≈98px） | `minimap.rs:313` + `editor.rs:202` 注释 |
| 位置 | 编辑器面板**右缘**，与内容区平齐 | `editor.rs:204-206` |
| 让位方式 | `TextEdit` **被压窄** `MINIMAP_W` | `editor.rs:260-262` |
| 开关 | `theme.show_minimap` + `Ctrl/Cmd+Alt+M` | **#67 M2 已落地**（PR #129） |

**为什么读成「第三栏」**：条带是**不透明**的、与内容区**等高**、且**一直占位**——
三个条件合起来就是一条独立的竖栏。侧栏 / 编辑器 / 预览是三栏，
minimap 让编辑区右边又出现第四条边界，读起来就是「编辑器被夹在中间」。

#### 设计

| 决策 | 选择 | 理由 |
|---|---|---|
| 形态 | **浮层**盖在编辑器右下角，**不占位** | 「不占位」是消除第三栏错觉的**唯一**办法 —— 只要还压窄 TextEdit，边界就还在 |
| 高度 | 视口高的 ~40%，最小 120px | 够定位又不遮住正文；行数多时按比例缩 |
| 不透明度 | 静止 ~35%，hover/拖动时 → 85% | 静止时"不存在"，交互时"在场"。**不用固定半透明** —— 固定值在浅色下会与正文抢对比度 |
| 位置 | 右下角，距边缘 8px | 惯例位置（VS Code minimap 同侧）；右下角最少与行号/滚动条打架 |
| 拖动 | 沿用 #68 的 grab 语义 | **#68 已在做这件事**，S3-1 不重复实现 |
| 折叠 | 复用既有 `Ctrl/Cmd+Alt+M` | #67 已落地，**S3-1 不新增开关** |
| 关闭态 | 完全不画、不占位 | 与现状一致（`show_minimap=false` 时零成本） |

#### 冲突面（**这就是必须等 #68 的原因**）

S3-1 要改的三处，与 #68 改的 `editor.rs` 区域**重叠**：

| S3-1 要改 | 位置 | #68 是否也改 |
|---|---|---|
| 条带矩形计算 | `editor.rs:199-206` | ✅ 重叠（`@@ -219,6`） |
| TextEdit 压窄逻辑 | `editor.rs:260-262` | ✅ 重叠（`@@ -242,9`） |
| `MINIMAP_W` 与让位断言 | `minimap.rs:313` / `:1098,1138` | ❌ 不碰（#68 改的是 `JumpInput` 349-390 与测试） |

即 **#68 的 `editor.rs` +84 行正好压在 S3-1 必须改的两处**。
现在动手 = 必然 rebase + 解决冲突，且是在刚吃过「布局回归」亏之后。

#### 验收标准（实现时逐条打）

1. `show_minimap=true` 时 **`TextEdit` 右缘贴视口右缘**（不再让位）——
   现有断言 `minimap.rs:1046-1051`「关闭 = 吃满剩余宽」的**镜像**版本要新写
2. 浮层不遮挡光标行：hover 透明度提升后仍能看清当前行内容
3. 拖影（#68 的 grab）落点与浮层位置**互不干扰**（两者都在右下角，需实测）
4. 浮层**不吃掉滚动条避让区**（现状 108px 里最右 10px 是给滚动条的，浮层不能盖住它）
5. 浮层几何断言：高度在 `[120, 视口高×0.45]` 区间，不越出视口
6. 明暗两主题 + 三平台截图目视（浮层的 35% 在浅色下是否还能看出是 minimap）

#### 重启条件

**#68 合入 main 后**即可开工。届时本节即为实现依据，无需重新设计。

### 6.3 症状 A 的真实代价（2026-10-08 实测订正）

原诊断写「顶部三条横栏吃掉 ~90px」，**是按「格式条 30px = 一行」估的，不对**。
900×600 实测：

| 条栏 | 实测 | 依据 |
|---|---|---|
| 标题栏 | 36px | 截图 y=0..35 |
| 菜单栏 | **29px**（原估 ~24） | 截图 y=36..64 |
| 格式条 | **63px（两行）** | headless 量 `min_rect` @240px + 截图目视 |
| **合计** | **128px** | 占 600px 窗口高的 **21%** |

**格式条是其中最大的一项（63px，占一半）**，而它之所以是两行：编辑区列在
900px 窗口下只有 **240px**，格式条一行要 **331px**（§5 实测）→ `horizontal_wrapped`
必然换行。

**同一个代码库里已有正解**：`ui/tabs.rs` 绘制标签条时用
`ScrollArea::horizontal` 而**不是** wrap，其注释写明理由 ——
「换行会让高度随标签数成倍增长，**把编辑区顶得上下跳**；单行 + 滚动高度恒定」。
格式条用了 `horizontal_wrapped`，正好踩了标签条当年避开的那条坑。

#### 待坤哥拍板的三个选项（我不擅自改）

| 选项 | 省 | 代价 |
|---|---|---|
| **A. 格式条改水平滚动**（照标签条先例） | 33px | 240px 列下「更多」会滚出视野 → 九个低频动作只能靠菜单栏触达，**削弱 S2-2 的成果** |
| B. 「更多」改纯图标（⋯）并压缩按钮内边距 | 约 20px | 仍 >240 仍两行；且「更多」变图标后可发现性下降（与 S2-2「可发现性」取向相反） |
| C. 列宽不足时**整条隐藏**，格式全走菜单栏「格式」 | 63px | 按钮「消失」是行为变更；且菜单栏已有全部 17 项，本就不丢可发现性 |

**我倾向 A**：它与本项目已在标签条上验证过的做法一致，且不新增任何概念；
「更多滚出视野」在 240px 这种极端窄列下可接受（用户可临时拉宽窗口或用
菜单栏）。但这属于**产品观感取舍**，且 S2-2 刚改过一轮、其守门测试
（`direct_row_is_inline_plus_list_only` 等）仍新鲜，**不宜我连续再动**，
故列出来由你定。

**重启条件**：若编辑区常态宽度 ≥340px（格式条一行放得下），本节自动失效
—— 问题根本不存在。降 `PREVIEW_DEFAULT_W`（420→340）是最直接的解法。
